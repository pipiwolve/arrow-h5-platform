## 摘要

- 对象：分支 `experiment/cloud-function-call`，`DEVICE_ROUTE=cloud`、`IOT_MODE=real`、家庭 933、11 台设备（除 1 台浴霸外全离线）。
- 语料：`2026-10-12-客户指令集.md` 的 80 句。80 句里 **0 句带房间或设备名**，全是「打开自动翻盖」「开大冲」这种只有动作的说法。
- 第一轮每句新开一间房：80 句 **0 次函数调用**。54 句只回「准备发给平台」，25 句没有任何回执，1 句反问「是哪一台」。
- 第二轮同一间房连发：80 句里 **1 次函数调用**，1 句只回话，78 句静默。见第 4 节 [[#4 第二轮：单房间连发]]。
- 决定性问题不在本机代码，在控制台：`control_device` 的 `deviceName` 参数描述写着「多台都可能命中时不要调用，先问是哪一台」（`产品文档/后台控制台交付配置.md:115`）。这 80 句每句都能命中多台，按这句描述模型就不该调用。
- 当前代码也不是纯云端。`src/turn.mjs:98` 仍在跑 `completeAction`，`src/turn.mjs:160` 的 `chooseDevice` 仍在按原话收窄并补 `deviceName`。只是这批句子压根没有 `[F]` 进来，这一层没被触发。

## 1 判定口径

| 结果 | 判定 |
| --- | --- |
| 调用并执行 | 收到 `[F] control_device`，闸门放行，`demo.result` 为 `EXECUTED` |
| 调用但出卡 | 收到 `[F]`，`deviceName` 不在清单里，页面出选择卡或确认卡 |
| 只回话 | 有助手正文，没有 `[F]` |
| 静默 | 等满 26 秒，除用户气泡外没有新增节点 |
| 反问 | 正文里问「哪一台」 |

## 2 协议

服务：`PORT=8788 IOT_MODE=real node server.mjs`，`DEVICE_ROUTE` 不设即 cloud（本报告在 `experiment/cloud-function-call` 与 `release/cloud-console` 上成立；`release/local` 要显式写 `DEVICE_ROUTE=cloud`）。

- 第一轮：每句新开页面、新进房间，等输入框可用后 2 秒发送，最多等 32 秒，无回复重试一次。
- 第二轮：同一间房按语料顺序连发，每句最多等 26 秒，句间停 4 秒。
- 逐句截图在 `截图/`（第一轮）与 `单房间/截图/`（第二轮）。对照实验的截图在 `对照/`。

## 3 第一轮：每句新开房间

| 结果 | 条数 |
| --- | --- |
| 调用并执行 | 0 |
| 调用但出卡 | 0 |
| 只回话 | 54 |
| 静默 | 25 |
| 反问 | 1 |

54 句的正文全是「准备发给平台。」，没有一个 `[F]`。反问的那句是「自动翻盖关了」，回复「准备将客卫 AKB1621-4G 智能坐便器的自动翻盖关闭。因同一房间有多台同型号设备，需确认您指的是哪一台。」

另外有 1 句（「别自动润瓷了」）浏览器侧 `Runtime.callFunctionOn` 超时，不影响该行判定。

这轮还暴露了每句新开房间这个协议的问题：80 次里有 25 次静默、1 次页面调用超时、中途 2 次进房 90 秒超时。但它是逐句独立的机会，测出来的是「这一句云端调不调」，所以第 3 节的数按它算。

## 4 第二轮：单房间连发

同一间房按语料顺序连发 80 句，句间停 4 秒，每句最多等 26 秒。

| 结果 | 条数 |
| --- | --- |
| 调用并执行 | 0 |
| 调用但出卡 | 1（第 11 句「把自动翻盖关掉」） |
| 只回话 | 1（第 18 句「把脚触感应打开」，回「准备发给平台」） |
| 静默 | 78 |

第 11 句的 `[F]` 里 `deviceName` 是「主卫 AKB1332-P智能坐便器」，本机 `trustedName` 不认，转成选择卡，候选 8 台马桶。

单房间并没有比新开房间好，反而更差：78 句没有任何回执。房间在助手没有出声的回合之后，下一句 `[T]` 多数不再产生输出。所以单房间这组只用来确认「云端确实不调用」，不能用来量逐句行为。

## 5 问题清单

### P1 只带动作、不带房间的句子，云端不调用函数

- 现象：80 句 0 次调用。回复统一是「准备发给平台。」或什么都不说。
- 复现：新开房间发「打开自动翻盖」，只出一句「准备发给平台。」，没有卡片也没有函数调用；同一句放单房间里发，26 秒内没有任何回执。
- 原因：`control_device` 的 `deviceName` 参数描述（`产品文档/后台控制台交付配置.md:115`）要求「只填清单里设备号那一串」并且「多台都可能命中时不要调用，先问是哪一台」。夜灯能命中 11 台、翻盖能命中 8 台，按这句描述模型就不该调用。控制台函数例句里恰好有「来个大冲」「冲一下」「夜灯开一下」，和这句描述自相矛盾。
- 处理：控制台侧改 `deviceName` 描述，删掉「不要调用，先问是哪一台」，改成「多台都可能命中时填房间+品类，例如 主卫坐便器，页面会让用户选」。本机侧先改了一段，见 P2，单独改不动这个行为。
- 佐证：`对照/清单2207字-只回话.png`、`对照/未点名房间-来个大冲-静默.png`

### P2 在本机清单里加指令，压不过函数参数描述

- 现象：把 `src/roster.mjs` 的「命中唯一一台时调用」改成「必须调用，多台填房间+品类」，同一批句子仍然 0 次调用，而且从「只回话」变成「静默」。
- 复现：改完 `roster.mjs` 重启服务，单房间连发「打开自动翻盖」「来个大冲」「开大冲」，26 秒内三条都没有任何回执。
- 原因：`[T]` 里附的清单是用户消息的一部分，`deviceName` 的参数描述是函数定义。函数定义优先。
- 处理：这条改动单独不足以修复，保留但必须配合 P1 的控制台改动。回滚点在 `git diff src/roster.mjs`。
- 佐证：无截图，三轮都是空房间，可复跑 `/tmp/arrow-browser/session-probe.mjs`。

### P3 云端填的 deviceName 是描述，不是设备号

- 现象：少数调用里 `deviceName` 是「主卫 AKB1332-P智能坐便器」「主卫坐便器」这类房间+型号描述，不是 `ARROW...` 设备号。
- 复现：单房间发「把自动翻盖关掉」，等待出卡。`cards.jsonl` 里记的是 `{"deviceName":"主卫 AKB1332-P智能坐便器","cmd":"switch_auto_closing","value":"off"}`。
- 原因：清单里一行有设备号、房间、型号、品类、在线状态、能力六段，模型倾向于复制可读的那一段。参数描述要求「逐字复制设备号」也没有完全约束住。
- 处理：本机 `chooseDevice` 用 `trustedName` 挡了这一层，不执行，转选择卡。这一层不能删，删了就会拿描述去打 IoT。
- 佐证：`对照/未点名房间-把自动翻盖关掉-出选择卡.png`

### P4 选择卡之后，房间拿到的函数回执是空的

- 现象：出选择卡的那一轮，助手没有说话。回给房间的 `[F]` 是 `{"result":"error","message":""}`。
- 复现：任意一轮走到选择卡，看 `/api/frame` 响应里的 `reply`。
- 原因：`server.mjs:221` 的 `message` 只取 `finished.receipt` 和 `finished.verdict.reasons`，出选择卡时两者都没有，`turn.finish` 只在 `spoken` 里给了「有多台设备符合，选一台再下发。」
- 处理：已改，`message` 和 `speak` 都补 `finished.spoken`。`server.mjs:224`、`server.mjs:227`。
- 佐证：见第 6 节的复验。

### P5 两种发句协议都不适合直接当验收口径

- 现象：每句新开房间 80 次里 25 次静默；试验中途另有 1 次页面调用超时、2 次进房 90 秒超时。单房间连发 80 句里 78 句静默。
- 复现：`/tmp/arrow-browser/run80.mjs`（每句新开）与 `run80-session.mjs`（单房间）各跑一遍，对比静默数。
- 原因：每句新开要重走授权和开场白，房间创建本身有失败率。单房间里，助手没出声的回合之后，下一句 `[T]` 多数不再产生输出，越往后越沉。
- 处理：逐句判定用「每句新开房间」，它测的是这一句云端调不调；单房间只用来验连续对话和上下文，不参与逐句成功率。要量真实体验，得按人说话节奏一句一句等回执，不能连发。
- 佐证：`/tmp/arrow-browser/run80.log`（54 次只回话）与 `单房间/results.json`（78 次静默）。

### P6 当前代码不是纯云端

- 现象：`/api/config` 返回 `deviceRoute: "cloud"`，`public/app.js:768` 的本机拦截确实关掉了，但 `src/turn.mjs:98` 的 `completeAction`、`:160` 的 `chooseDevice` 还在跑。
- 复现：`grep -n "completeAction\|chooseDevice" src/turn.mjs`。
- 原因：这次只改了入口和送帧，补槽这一层没动。
- 处理：要不要删取决于 P1 的结论。控制台不改，删了这层只会让「云端填描述」变成「直接打 IoT」；控制台改了，再删才安全。已加 `DEVICE_FILL=off` 开关，见 6.3。
- 佐证：`docs/测试报告/2026-11-10-纯云端分选.md` 第 4 节第 1 条。

## 6 已改与复验

### 6.1 已改：选择卡的回执不再为空（P4）

`server.mjs:221` 的 `message` 与 `speak` 补上 `finished.spoken`。改完后用云端形状的帧直接打 `/api/frame` 复验：

```bash
curl -s -X POST http://127.0.0.1:8788/api/frame -H 'content-type: application/json' \
  -d '{"sessionId":"hs_probe","frame":"[F]:{...deviceName=主卫坐便器, cmd=switch_watering...}","userText":"来个大冲"}'
```

改前 `reply` 是 `{"result":"error","message":""}`，改后是：

```json
{"result":"error","message":"有多台设备符合，选一台再下发。",
 "post_function":[{"type":"text","content":"有多台设备符合，选一台再下发。"}]}
```

### 6.2 已改：设备清单附录不再要求「唯一一台才调用」（P2）

`src/roster.mjs` 的头三行和末行改成「即使没点名房间也必须调用 `control_device`，多台时 `deviceName` 填房间+品类」。服务重启后清单从 2207 字变成 2351 字。

这条单独没有效果：同一批句子在改前改后都是 0 次调用，改后还多出静默。原因见 P2，函数参数描述的优先级高于用户消息里的附录。改动保留，但要等控制台一起改。

### 6.3 本机补槽层：默认保留，可用开关切三种模式（P6）

`src/turn.mjs:169` 和 `:196` 保留，默认仍然补槽。`DEVICE_FILL` 现在有三种值：

| 值 | 本机做什么 | 用在哪 |
| --- | --- | --- |
| `on`（默认） | 补空字段 + 收窄，多台出卡 | 旧路径 |
| `off` | 只校验，填错拒绝 | 量云端准确率 |
| `card` | 按 `cmd` 算候选，模型填的那台排第一，出卡点了才下发 | H5 上线形状 |

`/api/config` 的 `deviceFill` 返回模式字符串，`deviceCard` 在 `card` 下为 `true`。

`off` 模式用云端形状的帧打 `/api/frame` 复验过三种情况：

| 帧内容 | 结果 |
| --- | --- |
| `deviceName=ARROWToilet17332949200780`、`switch_watering/on` | `demo.gate` allow，落到 `demo.result` |
| `deviceName=主卫 AKB1332-P智能坐便器` | `demo.gate` deny（`设备不在该家庭`），不出选择卡 |
| 漏 `deviceName` | `demo.gate` deny（`指令项缺少 deviceName 字段`） |

浴缸进水这类高危动作仍然停在 `demo.gate` confirm，等页面确认。

`card` 模式复验过四种情况，都是同一批云端形状的帧：

| 输入 | 结果 |
| --- | --- |
| 「来个大冲」，模型填主卫 AKB1332-P | 出选择卡，6 台能大冲的马桶，主卫那台排第一 |
| 「把主卫坐便器的大冲打开」 | 出选择卡，只剩主卫 2 台 |
| 点客卫 akb162111 | `demo.gate` allow，`demo.result` EXECUTED，不再二次出卡 |
| 同一张卡点第二次 | 409 `这张选择卡已经下发过` |
| 「把主卫浴缸进水打开」 | 出选择卡 1 台，点了之后停在 `demo.gate` confirm，再确认才下发 |

`card` 模式里模型填什么决定卡片的第一位，不决定下发哪台，所以它编造设备号也不会把指令打进错的机器。

同一批帧在 `on` 模式下，后两种 `off` 的结果都会转成选择卡，这也是上一版能出卡的原因。

### 6.4 需要控制台侧改的一条

`产品文档/后台控制台交付配置.md:115` 的 `deviceName` 参数描述：

- 现在：「只填清单里『设备号』后面的那一串，以 ARROW 开头，逐字复制。不要填昵称、型号或房间。多台都可能命中时不要调用，先问是哪一台」
- 建议：「只填清单里『设备号』后面的那一串，以 ARROW 开头，逐字复制。多台都可能命中、用户没点名房间时，填『房间+品类』，例如 主卫坐便器，页面会列出候选让用户选，不要在正文里反问」

同时把函数例句里「来个大冲」「冲一下」「夜灯开一下」这三条和描述对齐，否则仍然矛盾。

这一条我改不了（在百度控制台），改完要按同一套 80 句复跑第 3 节的表。

## 7 结论

1. 纯云端承接不了这批语料。80 句里没有一句点名设备，云端函数定义又要求点名才调用，两条前提互斥。真实房间 0/80 次调用。
2. 本机占位槽不能先删。「选择卡」这条路径今天是 `chooseDevice` 给的，云端目前给不出来。[[2026-11-10-纯云端分选]] 里软件半段的 80/80 是按云端帧形状回放的契约测试，不代表真实房间的命中率；本轮就是那个缺口的实测。
3. 要先改控制台的 `control_device` 参数描述，再回来删本机补槽，最后按同一套 80 句复验。
4. 点名房间时云端可用：本轮对照实验里「把主卫坐便器的大冲打开」「把主卫镜柜的夜灯打开」都正常调用，前者直接执行，后者出两台同名镜柜的选择卡。问题集中在「只带动作、不带房间」这一类，而这批语料 80 句全属于这一类。
