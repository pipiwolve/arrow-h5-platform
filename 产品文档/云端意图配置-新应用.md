## 摘要

为验证云端能否独立填满设备槽位、提升 control_device 调用率而新建的互动应用配置：覆盖人设、control_device/create_scene/open_repair 三个 Function 与参数样例，并以 DEVICE_FILL=card/off 两种模式区分「上线形状」与「天花板测量」。

## 0 这份配置要解决什么

上一轮真实房间 80 句 0 次函数调用。原因不是本机，是控制台：`control_device` 的 `deviceName` 参数描述写着「多台都可能命中时不要调用，先问是哪一台」，而这 80 句全都是「打开自动翻盖」这种只带动作、不带房间的说法。

这一版要验的是**云端自己填满所有槽位**，本机不做任何补槽，只做校验。所以 `deviceName` 必须由模型自己选出具体设备号，没有「待定」这种把选择权交回页面的写法。

本机有两种跑法，用 `DEVICE_FILL` 切：

- `off`：填什么校验什么，填错拒绝。测模型选设备准不准，这组数是纯云端的天花板。
- `card`：模型选的那台排在候选第一位，其余候选由本机按房间和 `cmd` 算出来，点一台再下发。H5 有屏幕，这是能上线的形状，也顺带挡掉选错设备。

| 场景 | 模型怎么填 | 本机做什么 |
| --- | --- | --- |
| 点名房间或型号 | 在对应范围里选一台，填设备号 | 校验、过闸、下发 |
| 没点名 | 按第 3 节的选择顺序挑一台，填设备号 | 校验、过闸、下发 |
| 填了不存在的设备号 | 无 | 拒绝，卡片写明原因 |
| 漏字段或值不合法 | 无 | 拒绝，卡片写明原因 |
| `card` 模式下有候选 | 同上 | 出选择卡，模型填的那台排第一，点了才下发 |

本机补槽默认仍然开着（`on`），那是旧路径。要测云端，开关见第 7 节；不切到 `off` 或 `card`，模型漏填也会被本机悄悄补上。

## 1 应用与模型

新建互动应用，不要沿用现有 AppID。旧应用的人设、知识库意图和函数模板会互相打架，混在一起测不出结论。

| 项 | 值 |
| --- | --- |
| 应用类型 | 大模型实时互动 · VoiceChat |
| 角色名称 | 不要用「箭牌智家助手」，与预置角色重名，用 `ARROW 云端验证` |

## 3 Function：control_device

| 项           | 值                                                                                      |
| ----------- | -------------------------------------------------------------------------------------- |
| Function 名称 | `control_device`                                                                       |
| Function 描述 | 控制一台已接入的卫浴设备。用户要立刻开、关、冲水、进水、夜灯、翻盖、脚触、润瓷时必须调用这个函数。不点名设备也要调用，按清单顺序自己选一台。只说不调用不算完成。 |
| 执行前确认       | 否                                                                                      |
| 是否定时执行      | 否                                                                                      |
| 请求地址        | 发送 SDK 消息                                                                              |

Function 例句，一行一条，全部填进去：

```
来个大冲
帮我冲个马桶
冲一下
把自动翻盖关掉
打开自动翻盖
夜灯开一下
别夜灯了
启用脚触感应
开启自动润瓷
打开主卫浴缸进水
把主卫镜柜的夜灯打开
```

最后两条是「点名」的对照，其余是这轮没调起来的那一类。

参数：

| 参数名        | 类型     | 必填  | 参数描述                                                                                                                                                                                                                      |
| ---------- | ------ | --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| deviceName | String | 是   | 只能填清单里「设备号」后面那一串，ARROW 开头，逐字复制。用户点名房间或型号时，在对应范围里选；没点名时，按房间、品类、清单顺序挑一台。不要填昵称、型号、房间名，不要反问是哪一台，不要编造设备号。                                                                                                                  |
| cmd        | String | 是   | 只能取这七个之一：`switch_watering`（大冲）、`switch_night_light`（夜灯）、`switch_auto_closing`（自动翻盖）、`switch_kicking`（脚触感应）、`switch_auto_oiling_porcelain`（自动润瓷）、`switch_onoff`（电源开关）、`switch_water_in`（浴缸进水）。 |
| param      | String | 否   | 固定填 `switch`。                                                                                                                                                                                                             |
| value      | String | 是   | 只能填 `on` 或 `off`。打开、开启、启用、开一下填 `on`；关闭、关掉、停用、别再开填 `off`。大冲只能填 `on`。                                                                                                                                    |
| say        | String | 否   | 一句话说准备做什么，不超过 20 字，例如「准备冲水」。不要写已经执行。                                                                                                                                                                                      |

平台实测不认 `switch_watering_small`（小冲），该指令已从指令表删除。用户说「小冲」时本机返回「平台暂不支持小冲」，不要把 `switch_watering_small` 配进 `cmd` 枚举或例句。

## 4 Function：create_scene

| 项           | 值                                                |
| ----------- | ------------------------------------------------ |
| Function 名称 | `create_scene`                                   |
| Function 描述 | 创建一个按时间重复执行的设备场景。用户说每天、到点、自动执行时调用。马上操作一台设备不要用这个。 |
| 执行前确认       | 否                                                |


参数：

| 参数名           | 类型     | 必填  | 参数描述                                                                                                                                                                        |

| conditionList | String | 否   | JSON 数组字符串，每一项都要有 deviceName、cmd、param、value 和时间，例如 `[{"time":"22:00","deviceName":"ARROW0417663939524510","cmd":"switch_water_in","param":"switch","value":"on"}]`。不要只写时间对象。用户没说钟点就整项留空，不要索要。 |
| actionList    | String | 否   | JSON 数组字符串，每一项含 deviceName、cmd、param、value，字段口径与 control_device 相同，同样要填具体设备号，没点名就按房间、品类、清单顺序挑一台。                                                                         |

参数样例：

| 输入例句               | 参数名           | 参数值                                                                                                             |
| ------------------ | ------------- | --------------------------------------------------------------------------------------------------------------- |
| 每天晚上 10 点自动给主卫浴缸放水 | conditionList | `[{"time":"22:00","deviceName":"ARROW0417663939524510","cmd":"switch_water_in","param":"switch","value":"on"}]` |

## 7 本机要配合的三处

### 7.1 三种填槽模式：`DEVICE_FILL`

`src/turn.mjs:102` 按 `DEVICE_FILL` 分三条路走：

| 值 | 本机做什么 | 用来 |
| --- | --- | --- |
| `on`（默认） | `completeAction` 补空字段，`chooseDevice` 收窄，多台出卡 | 旧路径，本轮不测 |
| `off` | 什么都不补，闸门校验，不合法就拒绝，播报换成拒绝原因 | 量云端填槽准确率 |
| `card` | 按模型给的 `cmd` 算出候选，模型那台排第一，出卡，点了才下发 | 上线形状 |

`on` 和 `off` 的区别就是 `src/turn.mjs:169` 的 `completeAction` 和 `:196` 的 `chooseDevice` 跑不跑。

`card` 模式的几条边界：

- 候选由本机算：`cmd` 能执行的设备，原话点名房间就只看那个房间，模型填的那台排第一。
- 候选里没有模型填的那台（编造或填了描述），仍按能力出卡，不会因为它编错就拒。
- 一台候选都没有（这类指令没设备支持），退回 `off` 的行为，由闸门给拒绝原因。
- 点了以后直接过闸，不再走收窄，避免二次出卡。同一张卡点第二次返回 409。
- `create_scene` 不出卡，走 `off` 的行为。
- 高危动作是两步：先点设备，再点「确认执行」。浴缸进水就是两步。

`/api/config` 里 `deviceFill` 是模式字符串，`deviceCard` 在 `card` 模式下为 `true`。起服务后先确认这两项，再看 `DEVICE_FILL` 有没有生效。

`DEVICE_FILL` 已加进 `src/env.mjs` 的命令行直通名单，写在命令前面就能生效。`.env` 里没有这个键，不加就会当成没设。

```bash
DEVICE_FILL=card DEVICE_ROUTE=cloud IOT_MODE=real PORT=8788 node server.mjs
curl -s http://127.0.0.1:8788/api/config | grep -o '"deviceFill":"[a-z]*"\|"deviceCard":[a-z]*'
```

### 7.2 清单要给模型一条能自己走完的选择路径

`src/roster.mjs` 已经改成：按房间收窄，再按品类或型号收窄，仍有多台就取清单里排在最前面的那一台。没有这条，模型只能在「反问」和「编造」之间选一个。

当前 11 台设备，清单 2300 字左右，上限 6000。超过 30 台时指令表会被截断，模型拿不到可选指令。

### 7.3 和上一版（本机补槽）的差别

| | 上一版 | `card` | `off` |
| --- | --- | --- | --- |
| 没点名设备 | 模型填「待定」，本机按原话收窄出选择卡 | 模型自己填一台，本机按 `cmd` 算候选，它填的排第一 | 模型自己填一台，填错就拒 |
| 模型填错设备号 | 本机按原话换一台，不报错 | 不影响出卡，编造的那台不在候选里就不显示 | 拒绝，卡片写原因 |
| 每句要不要点 | 多台才点 | 都要点一次 | 不点 |
| 测出来的数 | 云端调用率 + 本机兜底 | 云端调用率 + 选对设备率（排第一的是不是用户想要的那台） | 纯云端调用率与填槽准确率 |

`card` 是能上线的形状，`off` 是天花板测量。两组数跑同一套 80 句，差多少就说明本机收窄还有多少价值。

## 8 新应用的验证步骤

1. 控制台建好应用，把人设、三个函数、参数样例、例句按第 2 到 5 节填完，保存并发布。
2. 本机换环境变量：`BRTC_APPID`、`BRTC_AK`、`BRTC_SK`、`BRTC_LICKEY` 换成新应用的，`DEVICE_ROUTE=cloud`、`IOT_MODE=real`，先加 `DEVICE_FILL=card`。起服务后确认 `/api/config` 里 `deviceRoute` 是 `cloud`、`deviceFill` 是 `card`、`deviceCard` 是 `true`。
3. 单句冒烟，发「打开自动翻盖」。判定：收到 `[F]`，页面出选择卡，候选是 6 台能翻盖的马桶，模型填的那台排第一。回一句「准备发给平台」不算过，卡里没有候选也不算过。点第一台，能下发并出结果卡。
4. 冒烟过了跑第一组全量：`card` 模式，同一套 80 句，每句新开房间。逐句记「有没有 `[F]`」「候选数对不对」「模型那台排第一时点它能不能下发」。
5. 再跑第二组全量：换 `DEVICE_FILL=off` 重启，同样 80 句。逐句记「`deviceName` 是否真实存在」「`cmd`、`value` 是否对得上原话」「被拒的原因」。
6. 通过标准：
   - 两组都要 80 句至少 76 句收到 `[F]`（95%）；
   - `card` 组候选数正确率不低于 95%（候选只含支持该 `cmd` 的设备，点了房间就只看那个房间）；
   - `card` 组点第一台能下发的比例，就是「云端自己选设备」的准确率，这个数要单独报出来；
   - `off` 组不存在设备号的占比低于 5%；
   - `cmd`、`value` 能对上原话语义（打开/关闭不要反）；
   - 「把主卫浴缸进水打开」在 `card` 组是两步：点设备、再点确认，最终执行成功；
   - 两组沉默率都低于 5%。

第 2 步的模式不切，本机就按 `on` 跑，模型漏填会被悄悄补上，两组数都不成立。

## 9 如果这版还不通过

按这个顺序判断，不用一次改一堆：

| 现象 | 说明 | 下一步 |
| --- | --- | --- |
| 给了选择顺序还是不调用 | 函数定义压不过人设或模型，云端这条路走不通 | 转方案：本机先收窄，再只把候选清单送云端填 `cmd/value`，设备由本机定 |
| 调用率上去了但 `deviceName` 乱填或编造 | 模型没把设备清单吃进去 | 先把清单砍到只留相关房间和品类再试一轮；还不行同上 |
| 只在带房间的句子上调用，不点名的仍然不调用 | 模型只肯在唯一解时才动手 | 把人设第 3 条提到第 1 条，并把反例（不调用）写进函数描述末尾再试一轮 |
| 调用正常但经常静默 | 平台侧回合问题，不是配置问题 | 单独查回合与 TTS，不要把配置推倒重来 |
