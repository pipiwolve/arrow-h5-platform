## 摘要

箭牌智家 AI 助手在百度「大模型实时互动」控制台上的交付配置。人设和知识库模板按仓库填写稿。三个 Function 按模板「箭牌iot平台控制」（ID 892）2026-11-09 的线上原文收录。

# 后台控制台交付配置

本文只收百度智能云「大模型实时互动」控制台上、绑到本 H5 互动应用的配置：自定义角色人设、三个 Function、知识库意图模板、四个知识库。密钥、AppID、AK/SK、license、IoT token 不写入本文。

本地建实例不传 `sceneRoleCfg`，也不传 `ragIntentTemplateId`。人设和知识库模板都用应用级绑定。改完人设后要结束当前通话，再开一次新通话。旧通话仍用改之前的人设。

口径日期：2026-11-09。三个 Function 以模板 ID `892` 的线上原文为准。知识库意图以 `产品文档/知识库上传/05-知识库意图填写稿.md` 为准，人设以 `08-人设修改.md` 为准。`07-下一步执行任务.md` 里的意图改名（「箭牌参数」「法恩莎故障」等）是后续任务，不纳入本版。

## 2. 人设

替换这个 AppID 自定义角色的全部提示词。

产品问答必须先检索再开口。回答最多三句：第一句就是结论，事实和很短的口头开头放在同一句。温度范围要同时说出下限和上限。没有这条事实时只说「说明书未记载」，到此停止。夜灯不亮、上电不能开机走知识库。设备操作仍只说「准备发给平台」，不要说已经执行。

```
#角色设定
你是箭牌智家助手，服务这个家庭已经接入的卫浴设备。语气短，一次只处理一件事。

#角色形象
问产品型号、参数、功能、故障、保养或保修时，先完成知识库检索再开口。
回答最多三句。第一句就是数字或结论，可以有很短的口头开头，但事实必须在同一句里。第二句只在检索原文写了条件时才说条件。然后停下。
问有哪些功能、都能干什么、介绍一下某款时，这一句就是检索原文里的功能名。
没有检索到对应事实时，只说「说明书未记载」，到此停止。不接常见坑距、其他型号或常识。温度范围必须同时说出下限和上限。
开、关、冲水、进水、夜灯、翻盖这些设备操作，只说准备发给平台。

#要求与限制
1. 立刻开、关、冲水、进水、夜灯、翻盖、脚触、润瓷，只调用 control_device。每天、到点、自动执行，才调用 create_scene。用户明确要报修或查报修进度，才调用 open_repair。
2. 问保修几年、客服电话、滤芯换不换、故障码是什么意思、上电不能开机怎么办、夜灯不亮先查哪里，走产品知识库，不调用 open_repair。
3. 用户消息里若有【家庭设备】，deviceName、cmd、param、value 从那段逐字复制。没有这段，或同一房间多台都可能命中时，只反问是哪一台，不要调用函数，不要编造设备号。
4. 参数提取不到时，用日常说法追问，例如问是哪一台、几点执行。禁止向用户索要 conditionList、actionList、deviceName、cmd、param、value、kind、say。
5. 型号、参数、保养、离线和能不能语音控制，走产品知识库。检索到的数字、档位和时长按原文说出。没有这条就只说说明书未记载。
6. 回答里不输出 JSON、代码块、字段名或设备号清单。
7. 不说已经执行、已经下发或已经成功。离线设备也可以提交，只说准备发给平台。
8. 座温、暖风、除雾、灯光亮度没有对应指令，告诉用户去 App 或面板操作。
```

自称写在人设正文里。控制台角色名称仍不要用「箭牌智家助手」。

## 3. Function

三个函数分工以人设第 1、2 条为准。

| 用户在说什么 | 调用 | 不调用 |
| --- | --- | --- |
| 立刻开、关、冲水、进水、夜灯、翻盖、脚触、润瓷 | `control_device` | `create_scene` |
| 每天、到点、自动执行 | `create_scene` | `control_device` |
| 明确要报修，或要查报修进度 | `open_repair` | 知识库 |
| 保修几年、客服电话、滤芯、故障码、上电不能开机、夜灯不亮 | 知识库意图 | `open_repair` |
| 型号、参数、保养、能不能语音控制 | 知识库意图 | 三个函数 |

多台都可能命中时，三个函数都不调用，先问是哪一台。

实验分支 `experiment/cloud-function-call` 与发布分支 `release/cloud-console` 默认 `DEVICE_ROUTE=cloud`；`release/local` 默认 `local`。云端模式下，打开、关闭、冲水、进水、夜灯、翻盖、脚触、润瓷不再走本机 `POST /api/intent`。这些句子连同当轮【家庭设备】以 `[T]` 送进房间，由下面三个 Function 填槽。问句仍进房间，但不附设备清单。报修和进度仍由页面出卡片。`DEVICE_ROUTE=local` 时恢复本机拦截。

### 3.1 control_device

模板 `892` 里这个函数的当前文案如下。请求地址是发送 SDK 消息。`docs/control-device-http示例.md` 只说明改成 HTTP 时槽位怎么走，表单文案以本节为准。

| 项 | 值 |
| --- | --- |
| Function 名称 | `control_device` |
| Function 描述 | 控制一台已接入的卫浴设备。用户要立刻开、关、冲水、进水、夜灯、翻盖、脚触或润瓷时调用。定时或每天自动执行不要用这个。 |
| 执行前确认 | 否 |
| 是否定时执行 | 否 |
| 请求地址 | 发送 SDK 消息 |

Function 例句：

```
来个大冲
帮我冲个马桶
冲一下
把自动翻盖关掉
夜灯开一下
别夜灯了
打开主卫浴缸进水
启用脚触感应
开启自动润瓷
```

控制台「执行前确认」选否。浴缸进水仍由 H5 闸门判为高危，页面确认后才打 IoT。见第 3.4 节。

| 参数名 | 类型 | 必填 | 参数描述 |
| --- | --- | --- | --- |
| deviceName | String | 是 | 只填清单里「设备号」后面的那一串，以 ARROW 开头，逐字复制。不要填昵称、型号或房间。多台都可能命中时，按房间、品类、清单顺序选一台，不要反问是哪一台 |
| cmd | String | 是 | 取值为 switch_watering、switch_night_light、switch_auto_closing、switch_kicking、switch_auto_oiling_porcelain、switch_onoff、switch_water_in 之一。大冲用 switch_watering。平台不认 switch_watering_small，不要填。 |
| param | String | 否 | 固定填 switch |
| value | String | 是 | 取值为 on 或 off。打开填 on，关闭、关掉、停用、别再开填 off。大冲只能填 on。 |
| say | String | 否 | 用一句话告诉用户准备做什么。不要向用户索要参数名 |

样例句「帮我把主卫坐便器的大冲打开」填出的槽位：

```json
{
  "deviceName": "ARROW01179421020631",
  "cmd": "switch_watering",
  "param": "switch",
  "value": "on",
  "say": "准备冲水"
}
```

`say` 只给播报。打到箭牌 IoT 的只有 `deviceName`、`cmd`、`param`、`value`。当前家庭编号是 UAT `933`，接口是 `POST /ext/v3/ai/control`。

模型填完槽后，房间推一帧。`content` 常为字符串，本机再解析一次：

```text
[F]:{
  "session_id": "1754555833139",
  "content": "{\"function_name\":\"control_device\",\"parameter_list\":[{\"deviceName\":\"ARROW01179421020631\",\"cmd\":\"switch_watering\",\"param\":\"switch\",\"value\":\"on\",\"say\":\"准备冲水\"}]}"
}
```

下发被平台受理时，页面回：

```text
[F]:{
  "session_id": "1754555833139",
  "result": "ok",
  "message": "平台已受理。",
  "post_function": [{ "type": "text", "content": "平台已受理。" }]
}
```

设备离线时 HTTP 仍可能是 200，body 为 `success: false`、`code: 500`、`msg: 设备离线`。这时回「设备当前离线，指令已送到平台，这一次没有执行。」审计记 FAILED。

### 3.2 create_scene

模板 `892` 的线上原文。截图里描述被收成「用户说每天、到点...」，全文在下表。

| 项 | 值 |
| --- | --- |
| Function 名称 | `create_scene` |
| Function 描述 | 创建一个会按时间重复执行的设备场景。用户说每天、到点、自动执行时调用。马上操作一台设备不要用这个。 |
| 执行前确认 | 否 |
| 是否定时执行 | 否 |
| 请求地址 | 发送 SDK 消息 |

「是否定时执行」是控制台自己的定时开关，保持否。定时语义写在 `conditionList` 里，不打开这一项。

Function 例句：

```
每天晚上 10 点自动给主卫浴缸放水
每天早上把夜灯关掉
帮我设一个定时冲水
工作日晚上自动关闭镜柜
到点就打开浴缸进水
```

| 参数名 | 类型 | 必填 | 参数描述 |
| --- | --- | --- | --- |
| conditionList | String | 否 | 从原话提取时间，填 JSON 数组字符串，例如 [{"time":"22:00"}]。用户没说具体钟点就留空，不要向用户索要 conditionList |
| actionList | String | 否 | 从原话和【家庭设备】提取要执行的设备，填 JSON 数组字符串。每项含 deviceName、cmd、param、value。不要向用户索要 actionList |
| say | String | 否 | 用一句话说明准备设置的时间、设备和动作 |

参数样例的输入例句是「把主卫浴缸的进水打开。」

| 命中参数名 | 参数值 |
| --- | --- |
| conditionList | `[{"time":"22:00","deviceName":"ARROW047663939595190","cmd":"switch_water_in","param":"switch","value":"on"}]` |
| actionList | `[{"deviceName":"ARROW047663939595190","cmd":"switch_water_in","param":"switch","value":"on"}]` |
| say | 准备建一个每晚放水的场景 |

`conditionList`、`actionList` 在 `[F]` 帧里是字符串，本机 `JSON.parse` 后再交给闸门。闸门 `src/policy.mjs` 要求条件和动作里的每一条都有 `deviceName`、`cmd`、`param`、`value`。页面描述里的 `[{"time":"22:00"}]` 会被拒绝。样例里的设备号 `ARROW047663939595190` 也不是当前家庭的主卫浴缸 `ARROW0417663939524510`。场景接口是 `POST /ext/v3/ai/scene`，`time` 的文档格式是 `YYYY-MM-DD HH:mm:ss`。开场示例里没有定时场景，这条尚未联调。

### 3.3 open_repair

模板 `892` 的线上原文。截图里描述被收成「只做跳转，不创建...」，全文在下表。

| 项 | 值 |
| --- | --- |
| Function 名称 | `open_repair` |
| Function 描述 | 打开报修入口，或查询已有报修的进度。只做跳转，不创建工单，也不控制设备。 |
| 执行前确认 | 否 |
| 是否定时执行 | 否 |
| 请求地址 | 发送 SDK 消息 |

Function 例句：

```
我家坐便器不出水了，要报修
帮我报修马桶
这个设备坏了，我要报修
查一下维修进度
报修处理到哪了
```

| 参数名 | 类型 | 必填 | 参数描述 |
| --- | --- | --- | --- |
| kind | String | 否 | 用户要查进度时填 progress，其他报修填 report。判断不了就填 report，不要向用户索要 kind |
| say | String | 否 | 用一句话说明准备打开报修或查询进度 |

参数样例：

| 输入例句 | 命中参数名 | 参数值 |
| --- | --- | --- |
| 我家坐便器不出水了，要报修。 | kind | `report` |
| 我家坐便器不出水了，要报修。 | say | 跳转前对用户说的一句话 |
| 帮我看一下报修进度。 | kind | `progress` |
| 帮我看一下报修进度。 | say | 我帮你查报修进度 |

`kind` 不是 `progress` 时，本机按 `report` 处理。这个函数不打 IoT，不创建工单。页面只给出 deeplink：

| kind | 跳转 | 卡片标题 |
| --- | --- | --- |
| report | `arrowhome://repair/create?from=ai_assistant` | 报修 |
| progress | `arrowhome://repair/list?from=ai_assistant` | 报修进度 |

「保修几年」「客服电话多少」「显示 E1 是什么」不在这个函数的例句里。

### 3.4 指令表与闸门

`cmd` 只允许下表。`param` 都是 `switch`。取值必须是 `on` 或 `off`，不要用 `1`、`0`、`true`。

| cmd | 允许值 | 说明 | 适用品类 |
| --- | --- | --- | --- |
| switch_watering | on | 马桶大冲 | 马桶 01 |
| switch_night_light | on / off | 夜灯 | 马桶 01、镜柜 06 |
| switch_auto_closing | on / off | 马桶自动翻盖 | 马桶 01 |
| switch_kicking | on / off | 马桶脚触感应 | 马桶 01 |
| switch_auto_oiling_porcelain | on / off | 马桶自动润瓷 | 马桶 01 |
| switch_onoff | on / off | 开关 | 马桶 01、浴缸 04、镜柜 06 |
| switch_water_in | on / off | 浴缸进水 | 浴缸 04 |

平台实测不认 `switch_watering_small`（小冲），已从指令表删除。用户说「小冲」时本机返回「平台暂不支持小冲」，不要让模型调用这个 cmd。

座温、暖风、除雾、灯光亮度没有对应指令。人设要求告诉用户去 App 或面板操作。

闸门不在控制台里，在 H5 `src/policy.mjs`。模型填完槽也不等于已经下发。

| 检查 | 不通过时 |
| --- | --- |
| 动作只能是设备控制、建场景、打开报修 | 拒绝 |
| 一次最多 3 条指令 | 拒绝 |
| deviceName 必须属于当前家庭；cmd、param、value 必须在上表内，且该品类支持这条指令 | 拒绝 |
| `switch_water_in` | 高危，页面确认后才下发。确认单 5 分钟内有效 |
| 其余 `switch` | 中危。唯一一台时直接下发 |
| 报修 | 直接放行，只出卡片 |

设备号和在线状态不写进人设。用户要操作设备时，本机把【家庭设备】附在当轮文字后面，供模型逐字复制。清单取不到时不要编造设备号。

## 4. 知识库

模板继续用 `arrow_product_kb`（ID `10000101`）。执行位置保持平台侧知识库检索，不要改成发送 SDK 消息。每条意图只挂一个库。

模板描述：

```
用户询问箭牌AKB1357、法恩莎FLM0814S-Q、安华NiL125的功能、参数、用法、故障、保养或保修时使用。回答直接使用检索到的原文，第一句给出结论。检索没有该事实时说说明书未记载。用户要立刻操作设备、建场景或打开报修页时不使用本模板。
```

意图描述里不要写「准备查看」，不要写 900W、电话、故障码这些答案。数字从挂载文档里取。合格回答的第一句就是结论。

表单限制：意图名称最多 40 字；描述最多 1000 字；每条例句最多 40 字。名称只用汉字、英文字母、数字和下划线。

### 4.2 不要保留的旧意图

配完下面七条并确认每条已挂上文件后，删除这三条。不要改名复用，占位例句和旧库绑定会留脏。

## 6. 交付核对

在控制台上逐项看，不要靠本文代替线上页面。

1. 互动应用已绑定自定义角色，角色名称不是「箭牌智家助手」。人设正文与第 2 节一致。
2. 三个 Function 都是发送 SDK 消息。`control_device` 的五个参数与第 3.1 节一致。
3. `create_scene` 的三个参数都是非必填 String。描述、五条例句和样例与第 3.2 节一致。
4. `open_repair` 的 `kind` 非必填，取值是 `report` 或 `progress`。保修、客服、故障码不在它的例句里。
5. 知识库意图模板显示 `arrow_product_kb`。列表只剩七条，挂库关系是 1 与 4 箭牌、2 与 5 法恩莎、3 与 6 安华、7 对照。
6. 四条旧占位不在列表里：型号规格、语音能控制什么、保养或离线与报修说明。若第七节改名尚未做，列表里应仍是第 4 节的长名称。
